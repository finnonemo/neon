# Contextual banner

> Core's Contextual banner, compiled for the web: the `iOS=False` look at the Large text size. Generated by the Core sync; do not edit.

## Variant axes

| Axis | Values | Drives |
| --- | --- | --- |
| `Status` | Success · Warning · Error · Info · Caution major · Caution minor | colors |
| `Hierarchy` | Primary · Secondary | colors |
| `Artwork` | Badge (icon 3XLarge, stacked on top) · Icon (icon Large, beside the text) · None (icon hidden) | Container direction, Leading Icon text style, visibility |
| `Action` | None · Icon Button (close, top-right) · Button · 2 Buttons (both Fill, stacked) · Toggle | which action instances show, Content right padding |

6 × 2 × 3 × 5 × 2 = **360 variants**. Component properties: booleans `Title`, `Description`; text `Title text`, `Description text`.

## Layer tree (target)

```
Contextual Banner (288 wide, Hug)
└─ Container (VERTICAL | HORIZONTAL for Icon, Fill × Hug, min-height 80, gap 16, padding 16, radius 16, stroke 1)
   ├─ Leading Icon (TEXT)              fa-sharp fa-solid/3XLarge | /Large
   ├─ Icon button                      Icon Button only: xmark, Tertiary, Small, iOS = variant's; absolute top-right (y 4, right flush)
   └─ Content (VERTICAL, Fill × Hug, gap 8, right padding 32 with Icon Button for Icon / None)
      ├─ Title and Description (VERTICAL)
      │  ├─ Title (TEXT)               $subhead, Strong
      │  └─ Description (TEXT)         $subhead
      └─ Action (VERTICAL, Fill × Hug, left aligned, gap 0, padding 0)
         ├─ Button                     Secondary, Small, iOS = variant's; Hug | Fill for 2 Buttons; min size = its main's
         └─ Toggle                     Toggle only, Enabled, Toggled=True, iOS = variant's; Hug × Hug (64 × 48 | 48 × 48)
```

Since #129 (2026-11-02) both looks hold one `Toggle` (Style=Toggle only) where `Toggle - Switch` and `Toggle` Style=Default, Fill × 24 (iOS=False) were, and the action instances take their main's min size.

Every variant holds both buttons and the Icon Button, hidden unless its `Action` shows them. Only the 72 Toggle variants hold a toggle, the one that matches their `iOS`; the other variants' hidden `Toggle` was deleted when the iOS axis was added.

## `Components` variables

`Banner/Contextual/<Container|Icon|Label>/<key>/<Property>`, Tag's three levels under a two-part prefix. The old Banner vars were renamed in place to `Banner/In-line/…` (ids and bindings kept) so both banners sit under `Banner/`.

- **Container** is keyed by `Artwork`. Only `Layout flow` differs (Badge and None Vertical, Icon Horizontal); the rest are the same as In-line: padding 16, radius `Radius/16px (radius-lg)`, stroke 1, min-height 80 (radius 12 and stroke 2 before #129).
- **Icon** records are `…/Type token` since #129; the older `…/Style` and `…/Size` records are still in Figma.
- **Icon** is keyed by icon size: `3XLarge` (Badge), `Large` (Icon).
- **Label**: Title (Strong) and Description (Regular), both `$subhead`.
- `Content`, `Title and Description` and `Action` have no group: their gaps and padding are fixed in the base or set as literals, as in In-line.

## `Theme` tokens

Shared with In-line Banner, nothing new: every color binds `Theme/Banner/{{Status=*}}/{{Hierarchy=*}}/<background|border|text|icon>`.

## Usage

- Use a Contextual banner where In-line banner's uses apply but the action needs a full line under the message: a long button label, two stacked buttons, or a Badge on top. This is Uber's layout for long labels, where "the button drops to the next line below the message" (Usage, Wrapping and truncation).
- The rest is as for [In-line banner](banner.md): what to use it for and not, one at a time, inset, under three lines (Uber, Usage and Content).

### Hierarchy

This section says what each `Hierarchy` value is for. The shared vocabulary, the rules every component follows and the owner's calls H1–H4 are in [hierarchy.md](../hierarchy.md). The nested buttons follow Button's rules in [button.md › Hierarchy](button.md). The matched Uber page is **Banner**, the same page as In-line banner's; Message card was checked and set aside (Sources). Apple has no banner component.

The two banners share their Theme tokens, so a value means the same in both. In-line banner's tables apply here: [Hierarchy](banner.md), and [Hierarchy with Status](banner.md) for which Status takes which value (a recommendation).

| `Hierarchy` | Use for | Don't | Uber | Apple |
| --- | --- | --- | --- | --- |
| **Primary** | Recommendation: a message the user has to notice or act on, such as an error or a blocking warning. | Don't use it for promotion or passive status. Don't stack it with other banners (Uber: one at a time). | Low (the same look); Uber's High has no match (CB1) | none (Feedback) |
| **Secondary** | Recommendation: passive status, or an offer the user may take (the `Call to action` sample). | Don't use it for an error that blocks the user. | none | none (Feedback) |

#### Nested actions

Since CB5 (owner, 2026-11-09) the spec pins each action's `Hierarchy` and `Type` to these values, so verify catches drift; `Size` stays unpinned. Every Status and both banner Hierarchies hold the same action.

| `Action` | Nests | `Hierarchy` · `Type` · `Size` | Against the rules |
| --- | --- | --- | --- |
| Icon Button | `Icon button`, `xmark` (close, top right) | Tertiary · Default · Small | Agrees. A way out ([rule 4](../hierarchy.md)), Tertiary on the banner's own surface ([H3](../hierarchy.md)), and Uber's `Layout=Icon button`. |
| Button | `Button` | Secondary · Default · Small | Agrees. [Rule 3](../hierarchy.md), and Uber's `Layout=Text button`. The label follows Button's Secondary rule ([button.md](button.md)). |
| 2 Buttons | `Button` and `Button 2`, stacked, Fill | Secondary + Secondary · Default · Small | Conflicts. Uber allows one action. Rule 2 gives the preferred button the louder Hierarchy. Button's Pairs never put Secondary + Secondary on a main action and its way out. The owner kept it (CB2). |
| Toggle | `Toggle` | not a button | Uber has no Toggle Layout; the owner kept it (CB3). |

- **No Primary inside.** A Contextual banner sits inside its screen's context, so its action is never the screen's one Primary ([rule 1](../hierarchy.md), H1). This is also why H4's Related pair (Primary + Secondary) doesn't fit in a banner.
- **No close button next to an action.** `Action` takes one value, so a banner with a Button has no close button. With `2 Buttons` kept as Secondary + Secondary (CB2), a banner that needs both an action and a dismissal has no Tertiary way out; label the second button for what it does.
- **`Type` stays Default on every banner**, and the spec's `contrast` list checks the nested labels and close icon on each banner background (CB4).
- [hierarchy.md](../hierarchy.md)'s nester row says "Button actions per the banner's Hierarchy". The actions don't change with the banner's Hierarchy, as in In-line banner.
