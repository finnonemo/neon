# In-line banner

> Core's In-line banner, compiled for the web: the `iOS=False` look at the Large text size. Generated by the Core sync; do not edit.

## Variant axes

| Axis | Values | Drives |
| --- | --- | --- |
| `Status` | Success · Warning · Error · Info · Caution major · Caution minor | colors |
| `Hierarchy` | Primary (Status-tinted background, border the same color) · Secondary (`background-primary` + `border-subtle`) | colors |
| `Artwork` | Badge (icon 3XLarge) · Icon (icon Large) · None (icon hidden) | Leading Icon text style, visibility |
| `Action` | None · Icon Button · Button · 2 Icon Buttons · Toggle | Container properties (padding right differs), which action layer shows |

6 × 2 × 3 × 5 × 2 = **360 variants**. Component properties: booleans `Title`, `Description`; text `Title text`, `Description text`.

Modeled on Uber Base's Banner (Style × Hierarchy × Layout × Artwork), renamed to this system's words: `Hierarchy` already means Primary/Secondary in Button and Tag, and `Layout` collides with the `Layout` collection.

## Layer tree (target)

```
Banner (VERTICAL, padding 0, no fill)
└─ Container (HORIZONTAL, Fill × Hug, min-height 80, gap 16, padding 16 / R / 16 / 16, radius 16, stroke 1)
   ├─ Leading Icon (TEXT)          fa-sharp fa-solid/3XLarge | /Large
   ├─ Title and Description (VERTICAL, Fill × Hug, gap 0, no padding)
   │  ├─ Title (TEXT)              $subhead, Type Emphasis = Strong
   │  └─ Description (TEXT)        $subhead
   ├─ Icon button                  (Tertiary, Small, iOS = variant's; min size = its main's Hit target)
   ├─ Button                       (Secondary, Small, iOS = variant's, no leading/trailing icon; min size = its main's)
   ├─ Icon Buttons (HORIZONTAL, Hug × Hug, gap 0)
   │  └─ Icon button × 2   (Secondary, Small, iOS = variant's, icon add)
   └─ Action (VERTICAL, Hug × Hug, padding 0, gap 0)
      └─ Toggle                    Style=Toggle only, Enabled, Toggled=True, iOS = variant's; Hug × Hug (64 × 48 | 48 × 48)
```

Container owns all vertical padding; Title and Description has none, so a one-line banner is 16 + 48 + 16 = 80 and long descriptions grow it instead of clipping.

The live set holds only each variant's own action layer (see Open), so a Toggle variant has one of the two toggles, not both.

## `Components` variables

Raw values, mode `Value`, `ALL_SCOPES`, like the rest of the collection. Shaped like Tag: `Banner/In-line/<Container|Icon|Label>/<key>/<Property>` (renamed from `Banner/…` in place 2026-10-27, next to [Contextual Banner](contextual-banner.md)'s `Banner/Contextual/…`), three levels, the full property set repeated under every key. Names and values live in `banner.gen.mjs`; this section keeps the reasons.

- **Container** is keyed by `Action` (None · Icon Button · Button · 2 Icon Buttons · Toggle). Only `Padding right` differs: 0 next to the Icon Button, whose own 48 × 48 hit area supplies the inset;
- **Icon** is keyed by icon size, as in Tag and Link (`Tag/Icon/Large/Size = large`), not by the Artwork value: Badge uses `3XLarge`, Icon uses `Large`.
- **Label** is keyed by Title · Description; Title's Type emphasis is Strong.
- Groups are the generic Element words, not the Figma layer names (`Leading Icon` → `Icon`, `Title` / `Description` → `Label`). `Title and Description` (the vertical stack) has no group: its gap 0 and Hug sizing are fixed in the base.
- Text and icon styles are bound directly; their String variables are records. Icon records are `Banner/In-line/Icon/<size>/Type token` (#129); the older `…/Style` and `…/Size` records are still in Figma, since the engine never deletes. Action instances take their main's own min width and height; before #129 they bound the shared `Interactive/Medium/Interactive min-height`.
- **Element template addition:** `Component/Element/Text/Type emphasis` records the Type Emphasis mode, since Title's boldness otherwise has no record.

## `Theme` tokens

`Banner/<Status>/<Hierarchy>/<role>` (background, border, text, icon), each an alias. The Banner group exists so one template `Theme/Banner/{{Status=*}}/{{Hierarchy=*}}/<role>` resolves for every Status.

- **Primary** is Status-tinted: background and border both alias `Notifications/notification-<status>-background` in Light, so it reads borderless. In Dark the border is the hue's `/0A` (Caution: `White/0`), so it doesn't stack on the alpha fill (#119).
- **Secondary** is neutral: `background-primary` with `border-subtle`. Its icon aliases the Status's `Support/support-<status>` in both modes, except Caution minor in Light, which keeps `Navy/150` (#82). It was aliased to primitives (Info `Indigo/100`, Cautions `Navy/150`, …) before the Dark audit.
- Hierarchy lives only here: like Tag, Stroke weight is the same on both Hierarchies.

## Usage

- `Form validation` (Error, Primary, no action) and `Statuses` (Secondary Info, Success and Warning, each with the close button).
- Use an In-line banner for a message about the state of one page or feature, at the top of the page or next to the content it is about: form validation, inline callouts, Warning, Success and Failure states (Uber, Usage).
- Don't use it for an app-wide system message (Uber's System banner; we have none), or for short-lived feedback after an action, such as "Copied": use a [Snackbar](snackbar.md) (Uber, Usage).
- Show one at a time. When several fields have errors, put them all in one banner at the top or bottom of the form (Uber, Usage).
- Keep it inset from the screen edges; don't stretch it edge to edge (Uber, Usage).
- Copy: keep it under three lines on mobile, and give a clear next step. Use end punctuation only between two sentences (Uber, Content).

### Hierarchy

This section says what each `Hierarchy` value is for. The shared vocabulary, the rules every component follows and the owner's calls H1–H4 are in [hierarchy.md](../hierarchy.md). The nested buttons follow Button's rules in [button.md › Hierarchy](button.md). The matched Uber page is **Banner**: Message card was checked and set aside (Sources). Apple has no banner component.

Uber's rule: a banner's Hierarchy follows "the message's severity", with "high and low-contrast color combinations" (Usage, Hierarchy). Uber's two values look different from ours. Uber's High is a solid Status fill with white text (black on Warning). Uber's Low is a light Status tint with black text. Our Primary is the light tint, and our Secondary is neutral (BN1).

| `Hierarchy` | Look | Use for | Don't | Uber | Apple |
| --- | --- | --- | --- | --- | --- |
| **Primary** | Status-tinted background and same-colour border, `text-primary` | Recommendation: a message the user has to notice or act on before going on. Example: a failure or a form error. The `Form validation` sample is Error Primary. | Don't use it for passive status that needs nothing from the user. Don't stack it with other banners (Uber: one at a time). | Low (the same look). Uber's High has no match (BN1). | none. Feedback: "match the significance of the information to the way it's delivered" |
| **Secondary** | `background-primary` with `border-subtle`; only the icon carries the Status | Recommendation: passive status the user can check when they want to, such as Info or Success. The `Statuses` sample is Secondary. | Don't use it for an error that blocks the user. | none | none. Feedback: show status information "in a passive way", near the item it describes |

#### Hierarchy with Status

`Status` picks the colour and `Hierarchy` picks how loud the banner is. Uber chooses the Hierarchy by severity. The column below applies that to each Status and is a recommendation; the dismissal column is Uber's own text.

| `Status` | Uber | Uber says it is for | Dismissal (Uber) | `Hierarchy` (recommendation) |
| --- | --- | --- | --- | --- |
| Error | Failure (`Style=Negative`) | telling the user something failed, and optionally blocking them until it is fixed | stays until the user dismisses it or fixes the error | Primary |
| Warning | Warning | results may be undesirable or unexpected | stays or can be dismissed, depending on the context | Primary when the user should act before going on; Secondary when the banner only informs (the `Statuses` sample) |
| Caution major | none | — | — | Primary |
| Caution minor | none | — | — | Secondary |
| Info | Info (`Style=Accent`) | supplemental information about a status | usually needs no action; can stay, be shown a limited number of times per session, or be dismissed | Secondary |
| Success | Success (`Style=Positive`) | a task completed as expected | usually needs no action; can stay or be dismissed | Secondary |

#### Nested actions

Since BN4 (owner, 2026-11-09) the spec pins each action's `Hierarchy` and `Type` to these values, so verify catches drift; `Size` stays unpinned. The second `Icon Buttons` instance shares the first's name, so the rule reaches only the first. Every Status and both banner Hierarchies hold the same action, so the action doesn't change with the banner's `Hierarchy`.

| `Action` | Nests | `Hierarchy` · `Type` · `Size` | Against the rules |
| --- | --- | --- | --- |
| Icon Button | `Icon button`, `xmark` (close) | Tertiary · Default · Small | Agrees. Close is a way out ([rule 4](../hierarchy.md)), and a Tertiary Icon button is fine on the banner's own surface ([H3](../hierarchy.md)). Uber's `Layout=Icon button` nests a Tertiary circle button, Small. |
| Button | `Button` | Secondary · Default · Small | Agrees. Secondary is the default ([rule 3](../hierarchy.md)). Uber's `Layout=Text button` nests a Secondary pill, Small. The label follows Button's Secondary rule: short, with no noun when the button is next to its object ([button.md](button.md)). |
| 2 Icon Buttons | 2 × `Icon button` (`add`) | Secondary · Default · Small | Secondary is the Icon button default (H3). Goes beyond Uber's one action; the owner kept it (BN2). |
| Toggle | `Toggle` | not a button | Uber has no Toggle Layout; the owner kept it (BN2). |

- **No Primary inside.** An In-line banner sits inside its screen's context, so its action is never the screen's one Primary ([rule 1](../hierarchy.md), H1). The live set agrees.
- **`Type` stays Default on every banner.** Uber tints the nested button to match the banner's background ("Buttons on colors"). Ours keeps the translucent `button-secondary` fill, and the spec's `contrast` list checks the nested label and icons on each banner background (BN3).
- [hierarchy.md](../hierarchy.md)'s nester row says "Button actions per the banner's Hierarchy". The live sets hold one action set for both Hierarchies, so that row should say so. hierarchy.md isn't edited here.
