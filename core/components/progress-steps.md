# Progress steps

> Core's Progress steps, compiled for the web: the `iOS=False` look at the Large text size. Generated by the Core sync; do not edit.

## Anatomy and layer tree

Vertical step (`_Progress step`, `Direction=Vertical`):

```
_Progress step (variant root)   Fill × Hug, no fill, no padding
   │  ├─ Marker                 HORIZONTAL, 36 × 36, radius 18, centred; fill per State
   │  │  └─ Number | Icon       Number: Body/Subheadline 15/24 (Incomplete, Current, Disabled); Icon: fa-sharp fa-solid/Small `check` (Completed), `xmark` (Error); none on Skeleton
      ├─ Step label             Body/Callout 16/24, Fill × Hug, wraps
      └─ Optional label         Body/Subheadline 15/24, Fill × Hug, wraps; BOOLEAN `Optional label`
```

Skeleton swaps `Text` for `Skeleton` (VERTICAL, Fill × Hug, padding top 14, bottom spacing-07 (32)) › `Step label line` (80 × 8, `Skeleton/skeleton-background`), the Label block's bar (structure.md). The 14 centres the bar on the marker; the 32 keeps a Line's length between skeleton steps. The Marker stays, filled `skeleton-background`, empty. (Reversed by padding 38 · 38 on Standard, 20 · 20 on Compact, so the bar sits centred on the row's height.)

Horizontal step (`Direction=Horizontal`), form B:

```
_Progress step (variant root)   Fill × Hug, no fill, no padding
└─ Container                    VERTICAL, Fill × Hug, gap spacing-03 (8), centred
   ├─ Path                      HORIZONTAL, Fill × Hug, centred
   │  ├─ Line start             HORIZONTAL, Fill × Hug, no fill: keeps its width when its line is hidden, so the marker stays centred
   │  │  └─ Line                Fill × spacing-01 (2); BOOLEAN `Line start`, off on the first step
   │  ├─ Marker                 as Vertical
   │  └─ Line end               as Line start
   │     └─ Line                Fill × spacing-01 (2); BOOLEAN `Line end`, off on the last step
   └─ Text                      VERTICAL, gap 0, Fill × Hug, centred
      ├─ Step label             Utility/Footnote 13/20, centred, wraps
```

Skeleton: `Skeleton` (padding 6 · 0 · 6, centred) › `Step label line` 80 × 8.

The set:

```
Progress steps (variant root)   Fill × Hug, no fill, no padding
└─ Container                    VERTICAL, Fill × Hug
   └─ Steps                     SLOT of `_Progress step`; VERTICAL (Vertical) or HORIZONTAL gap 0 (Horizontal), Fill × Hug
```

- **Carbon's structure, and one departure.** The layer names, the single `State` axis, the `Optional label` BOOLEAN and the Skeleton bar are Carbon's. Carbon draws the line as the item root's left or top stroke, beside a 16 icon. Under a 36 marker a stroke can't sit centred, so the line is a layer in a `Path` column, as Base and v2 draw it. Carbon's `Min-width` / `Min-height` spacers aren't drawn: the step is Fill in its set, and the Text's padding gives the height.
- Steps is a Slot (figma-instances.md). Its default content is four `_Progress step` instances, numbered 1–4, with their `State` and text pinned per Direction, as Segmented control's three default items. A designer sets `State`, `Number` and the texts on each item, and turns the end lines off.
- Horizontal A (segments + the current step's label, the map's form) is in 's frame for Q1; it would add a `Segment` tree and a Label block on the set.

## Usage

- Vertical: an order's status in full (Port's Toggletip, Investment Call's order page): 3 to 5 steps, a date or an expected time in each Optional label.
- Vertical reverse: the same steps read from the newest down, as an order history or timeline: step 1 at the bottom.
- Horizontal: the same status compact, short Step labels ("สั่งซื้อ", "ตัดเงิน", "ยืนยันราคา", "ได้รับหน่วย"), no Optional label.
- Error: the failed step says what happened and what to do ("ตัดเงินไม่สำเร็จ / ยอดเงินในบัญชีไม่พอ ลองสั่งซื้ออีกครั้ง"); the steps after it stay Incomplete.
- Skeleton while the order's status loads; a list that failed to load is the Pattern's error with its retry, not an Error step.
- Not this: one amount over time is Progress bar; a wait with no steps is Progress circle; a tappable step list (a wizard's navigation) is out, as Progress steps isn't interactive.

### Hierarchy

Which `Hierarchy` and `Type` its nested buttons take, and why. The rules (1–6) and the owner's calls (H1–H6) are in [hierarchy.md](../hierarchy.md); Button's own values are in [button.md › Hierarchy](button.md). Uber's [Progress steps](https://base.uber.com/6d2425e9f/p/82716e-progress-steps/b/06baa5) page gives no Hierarchy (read 2026-11-09), so the rules decide. "Agrees" checks the spec's pin; the set is built from the spec.

| Slot | Pin | Rule | Agrees |
| --- | --- | --- | --- |
| Progress step, Icon button "Secondary action" (`pen`) | `Secondary · Default · Small` | rule 3, H3 | yes |
| Progress step, Icon button "Primary action" (`ellipsis`) | `Secondary · Default · Small` | rule 3, H3; the layer's name isn't its Hierarchy | yes |
| Progress step, Button "Action" | `Secondary · Default · Small` | rule 3: an inline action in a row ([button.md](button.md)) | yes |

- A step's own action stays Secondary: the screen's Primary is elsewhere (rule 1).
