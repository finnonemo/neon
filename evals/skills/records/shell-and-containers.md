**Containers: no difference.** None of the four builds wraps a group in a card or puts a shadow on a region; groups are separated by space and hairlines. The baseline does the same, so this scenario does not show what the containers wording changed.

**Shell fixed: broken once, before the sidebar rule.** The `9fd0167` run added a `toolbar` prop to `SimpleLayout.tsx` and put a list of advisors in the sidebar, though the request named one advisor. The two runs at `67bd78e` changed no file under `src/layout/`. The baseline changed none either.

**Sidebar is the menu: met at `67bd78e`.** The one-advisor run left the sidebar without a record list and built in `ContentLayout`. The team run passed `sidebar={null}` and an empty navigation, listed the eight advisors in a list pane with the detail beside it, and shows them as two views with a "Back to team" link only on narrow screens. It took `AppShell`, the starter's list and detail layout, which is what the owner asked for; the `9fd0167` run had taken `SimpleLayout`. The contract at that commit also allowed a list page and a detail page; the next commit names the list and detail layout as the one form and has not been run.

**List and detail layout from the start (`c8f0f3d`): taken, and the baseline takes it too.** Both later runs of the team request import `AppShell`, pass `sidebar={null}` and an empty navigation, put the eight advisors in its list pane, and change no file under `src/layout/`. The baseline does the same without the sentence, so this request does not show what the sentence changed; the one run that took `SimpleLayout` for a list was the one-advisor request at `9fd0167`. Neither report says which layout it took or why, though both give a thesis written before building. The baseline report notes a React style warning logged from the starter's `ResponsivePanes`, which the run left alone.

**One advisor on main (`e0f38df`): `ContentLayout`, shell untouched.** The request that once took `SimpleLayout` with a list in the sidebar was rerun on main. It took `ContentLayout` with the contact details and licences in the inspector, passed `sidebar={null}` and one menu destination, changed no file under `src/layout/`, and used no card or shadow. Its report gives the thesis written before building and does not say which layout it took or why. Its transcript holds no React style warning; that fix merged before the run.

**Columns and a dock (`61a3590`): the shell is kept and reported, but no layout is used.** The request asks for two columns that scroll apart and a notes panel docked along the bottom, which no shell layout supplies. The baseline dropped the shell: its screen imports only `Logo`, draws its own header, has no sidebar, and its report does not mention the shell. The run on main changed no file under `src/layout/` and kept the sidebar and the phone bottom bar, but it did not build in a layout: `src/App.tsx` puts `Sidebar`, `InspectorView` and `BottomNav` together itself. Its report lists that as a departure, with the reason that `SimpleLayout` has no slot for the page title; it does not name the docked panel or the two columns as what did not fit. So the contract's "not edited" held, "build in the nearest one" did not, and the report said so in part. Neither build uses a card or a shadow.

**Columns and a dock, wording tightened (`30827e2`): built inside `SimpleLayout`, and the report says what did not fit.** The contract now says one of the shell's layouts renders the screen, its parts are not put together again, and the report names the layout taken and what did not fit. One rerun imports `SimpleLayout` alone, changes no file under `src/layout/`, and builds the two columns and the docked panel inside that layout's single pane. Its report has a "Layout gaps" heading: it names the single-pane layout, says no starter layout offers two equal columns with a full-width bottom panel, and lists what the layout leaves (an empty 64px strip above the content, a 360px sidebar holding only the logo). No card or shadow.

**The request is not one no layout fits: `MultiColumnLayout` supplies half of it.** That layout takes any number of columns and each scrolls on its own, so it supplies the two columns; it does not supply the docked panel, and its columns are a fixed 400px, which leaves 280px unused beside two of them at 1440px. The contract and the scaffold reference describe it as for explicit board or kanban tasks, and no run's report mentions it. The `30827e2` report's "no starter layout offers two equal columns" is therefore only partly true, and `SimpleLayout` may not have been the nearest layout. What the scenario shows is whether a run stays inside one layout when none supplies the whole screen, not what a run does when no layout comes close.

**The three builds opened at 1440 by 900: each has two columns that scroll apart and a panel that stays at the bottom.** The baseline's columns are 720px wide with 656px of scrolling height and no sidebar. The `61a3590` build's are 540px wide with 409px of scrolling height, under a 209px column heading that does not scroll, beside a 360px sidebar holding one menu destination. The `30827e2` build's are 540px wide with 568px of scrolling height, beside a 360px sidebar holding only the logo. Measured from the page; neither column was scrolled by hand and the notes were not saved.

**Columns and a dock, `MultiColumnLayout` described beyond boards (`47855b0`): the layout is taken, and the dock gets a shadow.** The contract and the scaffold reference now describe that layout by what it supplies (columns side by side that each scroll on their own: a board, or records compared in columns). One rerun imports `MultiColumnLayout`, changes no file under `src/layout/`, and its report names the layout and its gaps: no bottom region, an empty 64px toolbar strip above each column, unused space right of the columns at 1440px, and 400px columns in a sideways scroller at 375px. Opened at 1440 by 900: two 400px columns with 836px of scrolling height each, a 360px sidebar holding only the logo, 280px unused on the right. The panel is not inside a pane: it is a `position: fixed` layer over the columns, offset past the sidebar, and it carries a hand-written shadow (`shadow-[0_-8px_24px_rgba(0,0,0,0.08)]`), the first shadow on an on-page region in any run here. So the layout is now the nearest one, and "build what it lacks inside its panes" was missed for the dock. The shadow is not a miss: see the correction below.

**Columns and a dock on main, twice (`a375e78`): both results repeat.** Both runs import `MultiColumnLayout`, change no file under `src/layout/`, and name the layout in the report with "no bottom region" as what it lacks. Both draw the panel as a `position: fixed` layer beside the sidebar, 1080px wide over two 400px columns, with a shadow: `shadow-lg` in one, the same hand-written `shadow-[0_-8px_24px_rgba(0,0,0,0.08)]` in the other. One report gives its reason: the dock is "the only shadow, because both columns scroll beneath it". The second run also imports `SimpleLayout` and switches to it below 500px with a segmented control between the two advisors, so that screen is rendered by two layouts. With the `47855b0` run that is three of three taking the layout and three of three putting a fixed, shadowed dock outside its panes.

**Correction: the dock's shadow follows the skills.** An earlier version of this record called that shadow a miss of the containers rule. `skills/neon-audit/references/functional-patterns.md` lists "a dock while content scrolls beneath it" among the layers that float and take a shadow, and the contract says only a layer that really floats casts one. The three docks are fixed layers with columns scrolling beneath them, so their shadows are allowed; what the scenario's "no on-page region has a shadow" checks is on-page regions, and none of the builds shadows one. Two things remain: the hand-written `rgba` shadow in two of the three runs is not a value from the theme, and the dock sits outside the layout's panes because `MultiColumnLayout` has no bottom region.

**Requests that fit a layout, rerun with the tightened wording (`9bab030`): same layouts as before.** The one-advisor run took `ContentLayout` with a one-to-one agenda in the inspector, `sidebar={null}` and a menu; the team run took `AppShell` with `sidebar={null}`, an empty navigation and the eight advisors in its list pane. Neither changed a file under `src/layout/` or used a card or shadow, and both reports name the layout taken. The one-advisor run cost more than any earlier one (122 turns); one sample does not say whether the sentence caused that.

**Report names the layout: in eight of the twelve runs after the change, and not in any baseline.** The baseline report does not say why it took `ContentLayout`; the `67bd78e` runs name the layout and the reason, and the team run wrote its thesis before its first source file. The `9fd0167` run names `SimpleLayout` only to report the prop it added, and the two later runs (`c8f0f3d` and `e0f38df`) name no layout; the `61a3590` run took none. The three runs since the contract asked the report to name the layout (`30827e2`, the two at `9bab030`, `47855b0` and the two at `a375e78`) all name it.

What the runs do not show: whether the containers wording changes any build; whether the list and detail sentence changes a build, since the baseline also takes that layout for the team request, and the request that once took `SimpleLayout` took `ContentLayout` in one rerun, as the baseline and the `67bd78e` run had; whether a run builds inside the nearest layout when none fits, beyond one run after the wording was tightened; the run before it put the shell's parts together itself. Every run from `67bd78e` on, the team baseline included, was served a registry with the pane order fixed (sidebar, content, inspector); the first two were not, so their pane positions are not comparable. Whether a run takes `MultiColumnLayout` for columns that are not a board rests on three runs of one request.
