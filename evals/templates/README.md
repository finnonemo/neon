# Starter browser regressions

Maintainer-only tests; nothing in this directory ships with the plugin.

```sh
npm ci --prefix evals/templates
cd evals/templates
npx playwright install chromium
npm test
```

The runner assembles into a fresh OS temporary directory, installs the starter's locked dependencies and builds the untouched app. It then copies fixture source and the actual integration reference into that disposable app, builds again, and runs Chromium against its production preview. The temporary app is removed on success or failure. Tests use no backend or real records.

The fixture covers both controlled and uncontrolled content/detail navigation, state and scroll retention, focus return, breakpoint transitions, Detailed and Content Layout pane widths at the min and max of every desktop tier, all five layouts' navigation space, empty navigation, computed icon contrast, text on colored fills (buttons, checkbox, selected calendar day, dots and avatar initial under the starter and integration provider roots, light and dark), Tag and Avatar text contrast on every spectrum fill Neon overrides, the merged theme's keys and value formats against CDS's `defaultTheme`, font loading, and the integration example's styles and logo behavior. Tests inject a nonzero safe-area value through the same custom property used by the device inset; this does not certify physical-device behavior.

`cds-match.spec.mjs` holds the Neon base to the CDS starter. Three fixture screens (approval, extras with its overlays measured open, and expansion) are measured at 375 and 1440, light and dark, into `fixtures/cds-baseline.json`: sizes within ±1px, type exactly, colors, paddings, radii, borders and neighbor gaps. [measure.mjs](measure.mjs) lists every measured element with one selector per target, never a text search. Against the CDS app the spec checks that the baseline still holds; `npm run baseline` recaptures it after an intended CDS fixture or theme change. `npm test -- --target neon` builds the registry, serves it locally, creates the app with `shadcn init` from the Neon base, adds every registry component and runs every spec against it.

Neon's colors come from Core's Theme and its type sizes and line heights from Core's text styles, not CDS ([ADR 0009](../../docs/adr/0009-neon-matches-core-not-cds.md)), so the Neon target is held to the CDS baseline except for the differences recorded in `fixtures/core-differences.json`: one line per element and property, per screen, viewport and mode. A recorded difference that stops occurring fails the spec, as an unrecorded one does. A recorded box measurement (a width, height, radius or gap) is held to the same ±1px as the baseline, since macOS and Linux round a text's width a pixel apart; a type size, line height, weight or opacity is a set value and holds to its recorded number. After a Core sync or a retune changes what the Neon base renders, `npm run core-differences` records them again; read the diff before committing it, since every line must follow from a Core Theme token, a Core text style or the Counterpart's Core doc, never from a regression. A text style moves more than the text's own line: a control sized by its line height grows with it, and text one pixel larger wraps sooner.

The expansion screen (`?layout=expansion`) holds the registry expansion items (#164), one section per item, each in a `data-measure=<item>` hook. An item adds files only: its Counterpart in `fixtures/expansion/<item>.tsx`, its Neon side in `fixtures/neon/expansion/<item>.tsx`, and `expansion/<item>.mjs`, which exports its `screens` entries for measure.mjs and, optionally, an `a11y({ test, expect })` that registers its Neon behavior checks. Both screens find their sections with `import.meta.glob`, and the spec files load every item module through [expansion.mjs](expansion.mjs). A new item's baseline is captured with `NEON_CAPTURE_BASELINE=1 node run.mjs cds-match.spec.mjs`, which leaves `cds-layout-baseline.json` alone; the recapture must only add that item's keys.

`layouts.spec.mjs` runs on both targets: the Neon base's layouts from the registry face the same navigation, breakpoint, pane width, empty navigation, dark surface and logo checks. The integration, on-color, spectrum and merged-theme tests exercise the CDS provider and skip on Neon. `layout-match.spec.mjs` holds the Neon layouts to the CDS starter's geometry: every layout at 375, 768, 1024, 1280, 1440 and 1920 into `fixtures/cds-layout-baseline.json`, with the sidebar, panes, toolbars, bottom navigation and nav links within ±1px and the same page overflow. It finds elements by structure, so the frozen starter needs no test hooks; `npm run baseline` recaptures it with the match baseline.

`neon-a11y.spec.mjs` runs on the Neon target only: axe (WCAG 2.1 AA) on the approval, extras and expansion screens in light and dark, each expansion item's own checks, every Tag at 4.5:1 on its wash, the segmented control's arrow keys, focus returning from the Dialog and row menu, the Select closing on a pick, a polite toast with no provider in the screen, and the DatePicker's format in a `th-TH` browser (no Buddhist year). The one allowed violation is the dark destructive button (white on fgNegative, 4.32:1), provisional until #97.

`immersive-themes.spec.mjs` runs on the Neon target only: for each Immersive Theme on `ImmersiveLayout`, under OS light and dark emulation and with the app itself dark, the canvas, text, action button, disabled fill, focus ring, cards, popovers and logo tone match the generated `theme/css/immersive-themes.css`, `color-scheme` is dark for Ultra only, the secondary, outline, ghost, toggle, tag and segmented fills (`?controls`) take the theme with readable text, the page scrolls with the window with no inner scroller so a sticky section pins to the viewport, `html` and `body` carry the canvas behind overscroll, and the themed content keeps its full-bleed width and 1440px cap. Unthemed, the content keeps its own scrolling pane.

`--keep` leaves the assembled app in the temporary directory and prints its path, so you can preview and screenshot it.

The production preview listens on port 4178. Set `NEON_TEMPLATE_PORT` to run several suites at once, one port each (the preview uses `--strictPort`, so a taken port fails rather than sharing a server): `NEON_TEMPLATE_PORT=4179 node run.mjs --target neon`. Runs of one target from one checkout still share its report folder.

Reports, screenshots and failure traces go to `.local/evals/templates/<target>/` (`cds` or `neon`) in the repository and are uploaded by CI. Inspect screenshots for Thai/English wrapping and layout quality; successful assertions alone do not establish visual quality.
